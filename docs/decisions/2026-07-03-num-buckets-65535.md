# LayerStack bucket 数上限 65535 と direct GPU 経路

- **Status**: Accepted
- **Date**: 2026-07-03

## Context

LayerStack の `--num-buckets` は progress binning と per-bucket 重み形状を駆動する。
従来上限は 256 で、主因は `ShogiProgressKPAbs::bucket()` が `u8` を返していたことと、
sorted bucket layout (`padded_sort_batch`) が大 N で VRAM を爆発させることだった。

実験でより細かい progress binning を試すには、CUDA `gridDim.z` 上限 (65535) と整合する
範囲まで引き上げる必要がある。

## Decision

### 1. 上限 65535 (`u16::MAX`)

- `shogi_features::MAX_NUM_BUCKETS = 65535` を canonical とする
- bucket 返り値型は `u16` (`bucket = num_buckets - 1` が `u16::MAX` に収まる)
- `num_buckets = 65536` は reject (`gridDim.z` / index 型の範囲外)

### 2. デュアルパス GPU trainer

- `BUCKET_SORT_MAX_N = 256` 以下: 既存 bucket-sort + sorted tiled L1 経路
- 超過: **direct 経路** — `dense_mm_fwd_bucket` (L1)、
  `dense_mm_bwd_weight_bucket_unsorted` (L1/L2/L3 weight bwd)、
  `bias_grad_bucket` (L1/L2 bias bwd)

sorted layout は `padded ≈ batch + (N+1)×16` の保守的上界を持ち、
`N=65535` では実用不可。

### 3. VRAM

per-bucket 重み + Ranger optimizer state (`m`/`v`) はおおよそ `N × layer_dims` に比例。
`N=65535`・既定層次元では LayerStack 重み + optimizer だけで数十 GiB 級になりうる。
`--psqt` 時は `base_ft_in × N` が追加される。

### 4. フォーマット

`.bin` header の `num_buckets: u32` は既存のまま。save/load で
`MAX_NUM_BUCKETS` 超を reject する。

### 5. rshogi (推論エンジン)

本リポジトリ外の rshogi で以下が必要:

- progress → bucket の `u16` 化 (または内部 `i32` で 65535 まで)
- `.bin` load 時の `num_buckets` 上限緩和
- LayerStack / PSQT 配列の動的確保

`N > 256` の `.bin` は対応版 rshogi が merge されるまで推論に使えない。

## Consequences

- `N ≤ 256` の学習性能は従来と同じ sorted 経路
- `N > 256` は実験用途。L1 forward は non-tiled になり遅くなる
- progress.bin v2 trailer は `N-1` 個の f32 threshold (~256 KB at N=65535) で収まる
